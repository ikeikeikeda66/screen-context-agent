# ロードマップ

[English version](ROADMAP.md)

ScreenContext の次の拡張について、決定事項と作業順序を記録します。各作業は GitHub Issue で管理します。

## 目的

現在の ScreenContext は、部品（キャプチャ、OCR、暗号化履歴、MCP）の価値を理解できる人にしか評価されていません。次のリリースでは以下を目指します。

1. 記録データを**ユーザー自身が見て、制御できる**ようにする（削除、出力、監査）。画面記録ツールを信頼してもらうための前提条件です。
2. **MCPクライアントなしで価値が伝わる最初の体験**（Today ビュー）を用意し、一目で価値が分かるようにする。
3. **導入を短くし**、開発者がその体験にたどり着く前に離脱しないようにする。

ツール本体はシンプルに保ちます。ローカル完結、暗号化、LLM を内蔵しない、テレメトリを送らない。

## 決定事項

| # | 論点 | 決定 |
|---|---|---|
| 1 | 主対象 | MCPクライアントを使う開発者。Today ビューは MCP を知らない人への入口とする。企業は当面の対象外。 |
| 2 | 最初の体験 | LLM なしのローカル **Today ビュー**（ダイジェスト＋検索）。制御機能（削除、出力、アクセス履歴）も同じ画面に置く。 |
| 3 | 中断復帰 | Today ビューに「**直前の作業**」カードを置く。Pull のみ（通知なし）。作業セッションは、画面ロックまたは15分のアイドル（設定可）で区切った、アプリをまたぐ区間とする。 |
| 4 | UI の形態と書き込み権限 | `serve` とは別プロセスの localhost Web UI（`screen-context ui`）。**エージェント経路は読み取り専用、本人経路（CLI と UI）だけが書き込める。** 127.0.0.1、ランダムポート、ワンタイムトークンを Cookie に移行、Host/Origin 検査、書き込みは確認付きの POST のみ。UI では IDE も表示し、`policy.json` は常に適用する。 |
| 5 | 削除 | 3つの仕組み。**A. 保持期間**：プレビューの日数、OCR テキストの日数（テキストの初期値は無期限のまま）と使用量の表示。**B. 選択削除**：期間、アプリ、キーワード、ブロック、直近 N 分を指定し、FTS・プレビュー・rollup・outbox の根拠・監査記録まで連鎖して物理削除する。`secure_delete` を有効にし、取り消しは不可。出力済み・返却済みのデータには警告を出す。**C. 全消去**：鍵の破棄とデータフォルダの削除。除外ポリシーの追加は引き続き「隠す」が初期値で、「過去分も削除」はオプトイン。 |
| 6 | 出力 | 2つのコマンドに分ける。`backup`/`restore`：暗号化アーカイブ。鍵はユーザーのパスフレーズで包む（scrypt + AES-GCM）。全消去後でも別の PC に復元できる。`export --from --to --format jsonl\|md\|csv\|viking`：平文、ポリシー適用、監査ログに記録。`export DATE`/`push DATE` はこれに吸収する。 |
| 7 | 企業利用 | 今回：**設定リゾルバ**を1か所に集約し、優先順位を「管理設定 ＞ ユーザー設定 ＞ 初期値」とする。将来：構成プロファイル、ADMX、OS ログへの転送。管理サーバーは立てない。 |
| 8 | 監査 | 暗号化した `audit` テーブルに移し、検索語と返却したフレーム ID を記録する。閲覧は本人経路のみ（MCP では公開しない）。本人経路の書き込み操作も記録する。選択削除の対象に含める（削除操作そのものの記録は残す）。`audit.jsonl` は移行後に削除する。 |
| 9 | コード署名 | **Apple Developer ID は取得しない。** 固定の自己署名証明書を使い、アップデート後も画面収録の許可が維持されるようにする（要検証）。 |
| 10 | セキュリティ | クライアント別トークン（識別・失効・監査）、承認の仕組み（broker）による初回接続の承認、UI セッションと危険な操作での Touch ID / Windows Hello（5分操作なしで失効、画面ロックで即失効）。署名済みアプリ内に鍵を閉じ込める対策は先送り（Developer ID が必要なため）。 |
| 11 | 機微な入力 | フレームごと破棄する対象：Secure Input 中（macOS）／パスワード欄にフォーカスがあるとき（Windows）、カード番号（Luhn）、マイナンバー（チェックデジット）。連絡先アプリと決済ページは除外リストの初期値に入れる。**組み合わせルールは初期状態で ON**：OCR の5行以内に NAME ＋ ADDRESS・PHONE・DOB・EMAIL のいずれかがあれば、該当行を伏せ字にし、プレビューは保存しない。ルールは `policy.json` に置き、`pii-check` で判定を確認できる。除外件数（内容は含まない）を Today ビューに表示する。 |
| 12 | 配布 | 主な経路：GitHub Releases のビルド済み DMG（自己署名）＋ **GitHub Artifact Attestations**、Homebrew tap。副経路：ソースからビルドする `install.sh`。 |
| 13 | 順序 | フェーズ 0 → 1 → 2 → 3。一般公開はフェーズ3の完了後。 |
| 14–15 | Windows | 各フェーズを macOS で完了させ、次のフェーズに進む前に Windows で追従して実機検証する。一般公開は macOS を先行する。 |
| 16 | 既存機能 | `diary-material` は残し、ダイジェストとコードを共通化する。OpenViking は `export --format viking` に移す。proposal runner は実験的機能として残し、README の主な導線から外す。 |
| 17 | 成功基準 | テレメトリは送らない。フェーズ2の完了条件：メンテナーが2週間のうち10営業日以上 Today ビューを開いている。フェーズ3の完了条件：新しい環境で DMG のダウンロードから MCP 接続まで10分以内。 |

個人情報についての補足：組み合わせルールはリスクベースの考え方です。法律上は氏名だけでも個人情報に該当しますが、このルールは漏えいしたときに実害が大きい組み合わせを対象にします。

## 脅威モデルの変更

- 鍵を隔離しないため（決定10）、**同一ユーザーで動くプロセスは、画面収録の許可がなくても `screen-context serve` を起動すれば履歴を読めます**。クライアント別トークンと承認はクライアントの識別と許可のためのもので、同一ユーザーのマルウェアは防げません。README にその旨を明記します。
- 管理設定（将来）が防ぐのは事故や規程違反で、悪意のあるローカル管理者は防げません。

## フェーズ

### フェーズ0：技術検証と Windows の基準確認

- macOS：固定の自己署名証明書で、再ビルド後も画面収録の許可が維持されるか。
- macOS：アプリバンドルから Touch ID を呼べるか。Secure Input を検知できるか。
- Windows：Windows Hello、UI Automation によるパスワード欄の検知。
- Windows：現在のベータの実機検証（[WINDOWS.md](WINDOWS.md) の受け入れチェックリスト1〜7）。Windows でフェーズ1に着手する前提条件。macOS の技術検証と並行して進める。

### フェーズ1：信頼の土台（CLI）

設定リゾルバ、スキーマ v3、クライアント別トークンと承認、機微な入力のフィルタ、保持期間、選択削除、全消去、backup/restore、export、ドキュメント。その後 Windows で追従する。

### フェーズ2：Today ビュー

UI サーバーとセッションのセキュリティ、ダイジェストと検索、作業セッションと「直前の作業」カード、制御タブ、メニューバーの項目、2週間の実利用。その後 Windows で追従する。

### フェーズ3：配布（一般公開、macOS 先行）

アプリ内での indexer の起動、初回起動のセットアップ、CLI の同梱、リリースパイプライン、アンインストール、README の再構成、新しい環境での導入テスト。その後 Windows で追従する。

## 将来構想

- 署名済みアプリ内への鍵の隔離（企業からの要望やストア配布など、Developer ID を取得する理由が生じたら再検討する）。
- 管理設定：構成プロファイルのスキーマ、ADMX テンプレート、監査イベントの OS ログへの転送。
- 「直前の作業」の通知（オプション）。
- ベータ終了後の Windows コード署名。
